              📖 Strategy Guide — What does each strategy do? (click to expand)
              

                

                  🚫
                  
Baseline (No Limit) — Zero protection. Every tenant gets full server access. Purpose: shows what happens WITHOUT TenantShield. The victim's latency degrades badly.

                

                

                  🪣
                  
Request Count (Token Bucket) — Each tenant is capped at 15 requests per 10 seconds. Extra requests get HTTP 429. Purpose: stops volume floods. Simple, fast, and effective for basic rate-limiting.

                

                

                  🚦
                  
Concurrency Limiter — Each tenant can only have 2 simultaneous in-flight requests. 3rd request blocks or gets rejected. Purpose: prevents slow queries from hogging DB connections — unlike rate limiting, this limits "wide" concurrent load not just volume.

                

                

                  ⏱️
                  
Statement Timeout — Any SQL query from a tenant is auto-killed if it takes longer than 250 ms. Purpose: stops "expensive" noisy queries (like analytics) from starving the shared database. Best defense against heavy-query attacks.

                

                

                  💰
                  
Cost Budget Limiter — Each request is assigned a "cost" (normal = 1, analytics = 10). Tenant gets a budget of 25 cost units per 10 seconds. Purpose: smarter than counting requests — penalizes expensive operations more than cheap ones.

                

                

                  🛡️
                  
Combined Defense — Applies Request Count + Concurrency + Statement Timeout simultaneously. Any layer can block the request. Purpose: multi-layer protection. Best overall result — recommended for production.
